# 蜀南温泉运营系统一期 — Cline 项目规则

## 1. 最高优先级与工作方式

1. 开始任务前，先检查仓库现有代码、接口、测试和最新业务设计稿，再决定修改范围；不得凭旧对话、旧架构或想象的模块直接编码。Github仓库：https://github.com/XUGUANGCHEN7/wenquan.git
2. 需求冲突时，遵循：**用户本次明确指令 > 经确认的最新需求变更 > 本设计稿 > 旧版设计/历史讨论 > 个人技术偏好**。涉及资金、授权、硬件能力或合同规则的冲突，先指出并等待确认，不自行创造业务政策。
3. 每项非小型改动先说明目标、影响模块、数据/接口变化、风险、测试要点；未经授权不要扩大到其他模块。优先复用项目已存在的结构与依赖。
4. `brainstorming`、`writing-plans`、`executing-plans` 等通用 Skills 由 Cline 全局目录提供；**本文件只定义该项目的持续约束**，不要在项目中复制同名全局 Skills。
5. 若发现最新设计稿存在未确认事项：将其标为 `待确认/TODO`，提供不泄露真实资金或设备权限的模拟实现与可替换接口，**不要把猜测当已实现功能**。
6. 交付时说明修改文件、实现效果、已运行测试、尚未验证事项、需要甲方/设备商确认的问题；不得声称未实际执行的测试已通过。

## 2. 一期范围（必须遵守）

### 一期建设

- **两个独立微信小程序**：①购票会员小程序（公共浴室票、私汤预约、会员充值、余额/订单查看）创建在frontend_1的文件夹中；②私汤房二维码进入的**独立点餐小程序**（点餐、会员余额或微信支付）创建在frontend_2的文件夹中。
- **同一个业务会员账号与一份储值账本**：不重复注册、不开第二张会员卡、不收开卡费。
- **前台及商家 Web 后台**：订单/票券人工核验、手牌押金、发卡/回收、柜位分配、私汤分房与房态、充值活动、菜单、接单/制作/送达、退款异常及报表。创建在frontend_web的文件夹中
- **Python FastAPI 后端 + MySQL**：统一会员、购票/预约、库存、房态、点餐、会员账本、支付/退款及设备任务。创建在backend的文件夹中。
- **Windows 前台电脑 + USB NFC 读写器 + 本地设备服务**：用于实体手牌、柜位权限和私汤定时锁相关操作；实际接口能力以厂商 Windows SDK 和样机验证为准。

### 一期明确不做

- 不做闸机接入/自动核票；一期由**前台人工核验**并记录入园，闸机属于后续阶段。
- 不做手牌场内消费挂账、消费押金抵扣、离园统一清账或出口欠费拦截。
- 不假定已接入商家的其他 POS/收银系统。
- 不做自动退还/提现会员储值余额；该政策尚未确认。
- 不把厂商微信小程序插件直接当成 Windows DLL、FastAPI API 或已可用的设备网关。

## 3. 系统架构与数据边界

1. 后端使用 **FastAPI 模块化单体**；按 `会员身份`、`票券/订单/预约`、`房态与分房`、`储值账本`、`点餐`、`支付/退款/押金`、`手牌/柜位`、`设备任务` 等领域划清职责。暂不为一期引入不必要的微服务。
2. 两个小程序及 Web 后台使用同一套**带版本号的 HTTPS API**；菜单/价格、房态、余额、支付和授权由服务端统一决定，不在多个前端各自实现一套业务真相。
3. 前台 Web **不直接访问 USB、DLL 或厂家私有端口**；FastAPI 先创建和记录设备任务，Windows 本地服务从后端经认证 HTTPS **主动领取任务、执行并回传结果**。云端无需主动连接园区内网。
4. Windows 本地服务可使用 Python 或 C#，**取决于真实 DLL 的 ABI、32/64 位、依赖、许可证与运行环境**；在取得 SDK 前不固定语言、函数签名、通信端口或卡片结构。
5. 前台 Web 沿用项目已有框架与目录约定；如项目仍未初始化，可按既定讨论优先考虑 Vue 3 + TypeScript，但不要把该推荐误写成最新业务稿已经确认的技术版本。
6. MySQL 保存权威业务事实、状态机、交易与设备任务；缓存、消息队列、WebSocket 等只在有明确需求时增加，不能代替事务与持久化。
7. **云端/园区本地的最终部署位置尚未确认**；设计应支持环境配置与部署迁移，不擅自认定已选定某家云厂商、地域或固定服务器规格。

## 4. 会员身份与两个小程序

1. 系统以唯一 `member_id` 为业务会员主键，维护 `(appid, openid) -> member_id` 的登录标识映射；不同小程序的 OpenID **不能当成同一值**。
2. 只有在实际验证可取得 UnionID 时才能用它归并身份；否则通过**一次性授权、身份校验**将点餐小程序登录标识关联到已有 `member_id`。禁止静默合并或生成第二份充值余额。
3. 扫房间码的访客即使未绑定会员，也允许使用点餐小程序的**微信支付**；只有确认其对现有 `member_id` 的合法所有权后，才能查看或扣减该会员的余额。
4. 两个小程序各有 AppID；点餐小程序的微信支付需有正确的商户号关联及支付权限，调用支付时使用**该小程序自身 AppID 对应的 OpenID**。
5. 微信小程序 AppSecret、支付密钥和设备商密钥只能放在受控服务端/安全配置，不得放在小程序包、Web 资源或日志中。

## 5. 公共浴室票与入园

1. 每位实际入园游客必须有**一张独立且有效的公共浴室票**，即使同时购买了私汤预约也不能省略。一个订单可购买多人票与儿童票；儿童规则和价格由后台配置。
2. 参考票价：**平日 29 元/人次，周末及节假日 49 元/人次**；节假日及实际价格后台维护，每张票保存成交价格快照。
3. 每票仅允许**一次入园**，一期由前台人工核验并标记使用；离开后再次入园需重新购票，不能擅自实现扫码/刷牌重复入园。
4. 单人到店身份、票券、手牌、柜位要分开建模；多人订单逐人核验、逐人发牌。

## 6. 私汤预约、分房与清洁（高风险业务）

1. 一期有 **17 间私汤房**，每日固定五场：`10:00–12:00`、`12:30–14:30`、`15:00–17:00`、`17:30–19:30`、`20:00–22:00`；每场使用 120 分钟，最终使用结束后清洁 **30 分钟**，末场清洁到 22:30。
2. 基础价 **120 元/场**，含桑拿房；一个订单可购买多个**相邻场次**，基础价按场次数相乘。相邻场次必须保障**同一间房连续使用，中间不清洁，最后统一清洁一次**；不相邻场次必须分别下单与分房。
3. 用户预约时选择场次、填写**预计到店时间**，但**不选具体房号**；前台到店后分房。不能把预约创建时的内部库存核验误写成已经向游客确定房间。
4. 可售量按真实可用房间的完整**使用区间 + 最终清洁区间**计算，并排除已售预约、维修、人工占用与加钟冲突；**禁止简单把每场库存设为 17**。
5. 购买多个相邻场次时，必须检查**至少一间具体房间能够覆盖整个连续区间和最后清洁**；不能用“每一场单独还有名额”推断整段可售。
6. 待支付预占保留 **15 分钟**；支付完成且渠道核验成功才确认预约；超时、付款失败释放占用。使用事务/锁及可验证冲突检查，防止并发超卖、重复确认或失效后支付误占房。
7. **实际使用时长从前台分房生效起算满 120 分钟**（多相邻场次按购买总时长），结束后仍需 30 分钟清洁。固定预约场次与实际分房计时存在潜在冲突：分房前必须重新检查实际使用+清洁是否侵占下一笔已售预约。
8. 有冲突且无其他可用房时，**不得强行分房、发放房门权限、覆盖下一笔预约或静默顺延**；交由前台按业务方签认的改期/退款流程处理，并保留通知、处理人、原因及结果。
9. 房态至少区分空闲/使用中（含人满）/待清洁/清洁中/维护；未确认清洁完成**不能再次分房**。房态来自预约、实际分房、清洁和维护记录；人工改动以审计事件记录，不直接覆盖原始事实。
10. 加钟由前台办理：核验当前手牌与预约、后续时段可用、付款已确认后才可申请延长授权；是否需要**重新刷/写实体手牌**取决于真实 SDK/样机，不得仅改数据库就声称锁端已延期。加钟价格/时长由后台配置。

## 7. 手牌、储物柜与逐枚押金

1. 前台逐人核验订单、票券和**该枚手牌对应的微信押金支付已成功**，再发牌；押金状态未知/未付不能发放手牌。每人独立票券、到店记录、手牌及柜位绑定。
2. **每枚手牌独立押金责任及金额快照**；押金金额尚未确定，配置于后台。只收**微信支付**，不能使用会员本金或赠送金支付手牌押金。
3. 可一人代付多枚押金，但必须建立“押金支付订单 → 多枚独立押金责任 → 每枚独立退款单”的映射。**归还一枚即按该枚实际押金向原付款人的原微信交易申请部分退款**，不等待同行全部归还；累计退款不得超过原订单金额，注意渠道单笔部分退款次数限制，必要时拆分押金收款订单。
4. 收到实物并核对本次发放记录后，立即记录归还并触发该枚押金退款；**清卡失败不剥夺归还者的应退押金**，但卡片进入隔离待处理，不能再发给下一位。
5. 退款受理、处理中、成功、异常/关闭必须区分；只有微信退款通知或主动查询证实 `SUCCESS` 才显示退款成功。超时/重复点击沿用**同一个退款单号**查询/重试，不创建第二笔；每枚押金最多成功退一次。
6. 前台先**预占空柜**，再创建写卡任务；写入且必要时读回核验成功后，才正式绑定手牌/柜位。失败或结果未知不擅自释放预占或重新发放，必须核实卡上真实权限后补偿。
7. 发卡后应由同一手牌打开原分配柜；再次刷牌不重新分柜。归还手牌、回收卡片、柜位清理后才释放柜位。**一期不做在柜机首次刷牌时自动分柜**。
8. 已收押金但最终未发牌，应针对原微信交易安排退款，不遗留无手牌的押金责任。手牌实物、逻辑 `card_id` 与本次到店绑定是不同实体，挂失/解绑/复用必须留历史记录。

## 8. 独立点餐小程序与房间二维码

1. 每间房有一张二维码进入**独立点餐小程序**；**任何扫码者都可浏览、选餐并使用本人微信支付或经核实的本人会员余额支付**，不要求其是当前入住登记人。
2. 房间码仅用于定位**送餐房号**，不证明扫码者在场，也不授予会员余额扣款权限。页面明确展示房号，管理后台支持停用、重印房间码。
3. 创建点餐订单时后端必须检查房间**当前有有效使用记录**；绑定当次 `room_use_id` 与价格快照，空闲/清洁/维护时不得接收新订单。
4. 支付完成时再次验证**同一个 `room_use_id`**仍然可送达，不能只判断当前房间又处于“使用中”（可能已换客）。
5. 已付款但因房间结束/缺货/无法送达的订单进入**前台异常处理队列**；**不自动退款、不静默进入商家待接单队列**。由前台依权限决定是否退款并记录原因与结果；顾客主动取消、部分退款规则仍待定。
6. **支付确认且可送达**后才进入商家 Web 接单队列；接单、制作、送达状态可查询/更新，重复支付回调不得重复出单。

## 9. 储值余额、交易及财务规则

1. 一期充值活动仅支持 **“充 X 元，赠 Y 元”**；实付本金与赠送余额分账，供公共浴室票、私汤预约和私汤点餐使用。
2. **最新明确规则：消费先扣本金，余额不足再扣赠送金额；禁止沿用旧方案的“按比例扣本金与赠送金”。** 两小程序访问同一账本。
3. 游客端只展示**本金+赠送金合计可用余额**；商家后台必须能分别查本金/赠送、充值/消费/冲回明细。充值本金、赠送金、手牌押金、票款、点餐款分开记账。
4. 所有金额使用**整数分**；票价、私汤价、菜价、手牌押金和活动规则保存成交快照。客户端不能自行修改应付金额或余额扣减来源。
5. 余额流水采用**追加式记录**，原记录不被覆盖；按原订单的实际本金/赠送金扣减量分别冲回。支付通知、余额扣款、退款、设备任务均采用业务唯一号、数据库事务与幂等处理。
6. 门票/私汤/点餐可用微信或合规的会员余额付款；**充值和手牌押金仅使用微信支付**。支付结果以服务端验证的渠道状态为准，不以客户端“支付成功”页面为准。
7. **不实现自动退余额/提现**；顾客主动取消、部分退款、损坏/遗失扣押金规则尚未确认，不能擅自实现默认扣款/退款公式。
8. 退款时：订单若原用余额支付，按原本金/赠送实际扣款明细冲回；若原用微信支付，向原交易按渠道规则退款。点餐无法送达由**前台人工决定**是否退款，不得自行自动退款。
9. 维护微信交易号、商户业务单号、退款号、支付/退款状态与审计日志，进行日结及微信渠道对账；**未退手牌押金不视为票款收入**。

## 10. 硬件与厂商接口：只承认已验证的能力

1. 已收到的《柜锁小程序插件接口文档》仅证明**微信小程序插件**有蓝牙开锁、NFC 发卡/读卡/回收等函数；**不证明 Windows DLL 存在、可调用，或存在 HTTP API**。
2. 厂商 Windows 桌面软件的视频/操作资料只能证明其现有人工操作流程，不是 DLL 函数签名或接口授权证明；“蓝牙是 HTTP”等说法需正式技术资料确认。
3. 取得正式 Windows SDK/驱动、USB NFC读写器、柜锁和私汤定时锁样机前，使用**可替换适配器 + Mock/模拟器**；不得捏造函数名、返回码、设备协议、密钥结构或 SDK 兼容性。
4. 必须实测同一实体手牌能否同时持有**柜锁和私汤锁**权限，以及授权有效期、延期是否重写、挂失撤销、回收清卡、断外网后开锁。测试结果写入联调报告，模拟成功**不能代替实物验收**。
5. 设备任务至少区分 `待领取`、`已领取`、`执行中`、`写卡确认成功`、`失败`、`结果未知`；有独立 `task_id`、操作员、目标读写器、实体卡/柜/房标识与原始错误信息。任务超时**不等于设备一定没写卡**，不得在未知状态下盲目重试。
6. 写卡函数返回成功仅代表所定义的读写器/SDK操作结果；**不能据此断言柜门或私汤房门实际开过**，除非厂商另提供可信门磁/开门事件。
7. 本地服务离线或园区断网时，已发手牌能否独立开锁属于**待样机验证目标**；在线支付、在线核验订单、微信原路退款不得伪装为离线成功。返回网络后按唯一业务号补传并对账。
8. 厂商软件的授权卡初始化、设置卡及区域配置，继续视为独立的人工调试步骤；未取得 API 前不得宣称可由 FastAPI 全自动完成。

## 11. 安全、数据库与接口规范

1. 业务 API 统一鉴权、角色授权和数据归属校验；前台、接单商家、财务、管理员权限分开，普通接单账号不得直接改会员余额、退款或操作实体卡。
2. 状态变更必须有**操作人/设备、时间、变更前后状态、原因和请求号**；关键的改房态、人工改期、退款、强制开柜与设备补偿应留完整审计链。
3. 支付回调验签并核对商户、金额、订单；相同通知或重复点击只应改变一次业务状态。退款失败或结果未知应可查询/恢复，不允许用一条新交易掩盖失败。
4. 数据库通过必要的唯一约束、事务和资源锁定避免双人抢同一柜、同一时段超卖、重复发牌、重复扣款或退款；不要只依赖前端按钮禁用或 Redis 锁。
5. 数据结构、接口出入参、错误码和状态机放入可追溯的设计/OpenAPI文档；所有数据库变更使用迁移脚本，部署版本之间保持两个小程序的 API 兼容窗口。
6. 仅保存业务必需的个人资料；不要在日志、代码、截图或测试数据中放入真实 AppSecret、私钥、真实手牌密钥或游客身份信息。

## 12. 实施、测试与交付门槛

1. 一个任务聚焦一个可验证目标；较大功能先设计与实施计划，再开发、测试、审查。不得在没有确认 SDK 和业务规则时继续承诺“设备已接通”。
2. 优先编写测试：并发售卖不超房；连续多场只在最后清洁；实际分房晚于预约时间导致撞场；15分钟锁房过期与支付回调竞争；票券单次入园；多人发牌/多枚押金独立部分退款。
3. 必测统一会员映射与跨小程序余额使用、**本金优先赠送金后用**、退款按原来源冲回、重复微信回调、重复发卡/读卡、设备结果未知、清卡失败仍退款、房间换客后的旧 `room_use_id` 点餐付款。
4. 区分单元测试、接口/数据库集成测试、设备模拟测试、真实 Windows SDK+NFC读写器+柜锁/私汤锁联调测试。没有真实设备和测试记录时，交付结论只能是“模拟/待联调”。
5. 开发、测试、生产环境隔离；部署提供环境变量清单、数据迁移、备份与实际恢复演练、回滚方案。不能在生产环境直接试错刷卡和支付。
6. 前台异常看板需关注：**待处理退款、微信对账差异、发卡结果未知、Windows 本地服务掉线、房间占用冲突、待清洁超时**；每类异常应有明确人工处理步骤。

## 13. 不可自行填补的待确认事项

- 业务方对设计稿的正式签认；**固定场次与实际分房后满时长的冲突处理**、告知与补偿/退款权限。
- 每枚手牌的押金金额、损坏/遗失责任、真实微信支付部分退款次数/商户能力、异常退款人工处理权限。
- 门票与私汤取消规则、点餐顾客主动取消与部分退款规则、储值余额退还/提现规则（一期不实现）。
- 两个小程序 AppID、商户号关系、UnionID可获取性、无UnionID时的安全授权绑定流程。
- 正式 Windows DLL/SDK、USB NFC型号、柜锁/私汤锁卡片权限、延时/清卡/断网行为与设备状态回传能力。
- FastAPI/MySQL最终部署位置与现场网络拓扑、外网故障时的前台应急流程。

> **实施底线**：宁可把未经证实的能力标成 `待确认`，采用 Mock 并保留替换点，也不要生成看似完整但无法连接真实硬件、可能重复扣款或覆盖已售房间的代码。
