# 蜀南温泉运营系统一期设计

日期：2026-11-01
状态：已批准（2026-11-01）

## 1. 意图与范围

基于 `.clinerules/project-rules.md`，把现有原生小程序改造成购票会员端 `frontend_1`，新增独立房间点餐端 `frontend_2`、前台及商家 Web `frontend_web`、FastAPI/MySQL 后端和 Windows 本地设备服务。目标是交付可运行、可测试的一期业务骨架，而非把 Mock 支付或硬件模拟包装成生产验收。

一期包含会员身份映射、门票与单次人工核验、私汤连续场次库存与到店分房、统一储值账本、独立点餐、支付/退款状态、逐枚手牌押金、柜位和设备任务、商家出餐、异常看板及报表。不做闸机、场内挂账、自动退余额、默认取消/扣押金政策，也不假定已有微信支付商户能力或 Windows SDK。

## 2. 已选方案与约束

采用 FastAPI 模块化单体、SQLAlchemy 2/Alembic、MySQL 8；测试可用 SQLite 快速运行领域测试，并用独立 MySQL 容器执行约束和并发集成测试。两个小程序继续使用微信原生 WXML/WXSS/JavaScript；Web 使用 Vue 3、TypeScript、Vite、Vue Router 和 Pinia。设备服务使用 Python，定义适配器接口并仅提供显式 Mock 实现，真实 DLL 语言与签名待 SDK 确认。

所有端共用 `/api/v1`；金额只传输整数分。服务端决定价格、库存、余额、支付及权限。开发登录、支付、微信身份和设备均清楚标注为开发适配器；生产环境禁用不安全的开发默认值。AppSecret、支付私钥和设备密钥仅由服务端环境变量提供。

## 3. 代码与模块边界

- `backend/app/modules/identity`：会员、`(appid, openid)` 唯一映射、显式跨小程序绑定、角色鉴权。
- `catalog`：票种、儿童规则、充值活动、菜品和价格配置快照。
- `tickets`：多人订单、逐人票券、人工单次入园记录。
- `rooms`：17 房、五固定场、连续场预占、15 分钟过期、到店分房、实际满时长、30 分钟末次清洁、维护和冲突队列。
- `wallet`：同一会员本金/赠送余额、追加式流水、本金先扣、按原扣款来源冲回。
- `dining`：房间码定位、有效 `room_use_id` 校验、价格快照、支付后二次校验、商家接单/制作/送达。
- `payments`：微信/余额支付单、渠道回调验签边界、业务幂等、独立退款单与人工异常。
- `access`：实体卡、逻辑卡、到店绑定、柜位预占、逐枚押金及独立退款责任。
- `devices`：待领取/已领取/执行中/成功/失败/结果未知任务，本地服务认证轮询与回传；未知结果禁止盲目重试。
- `audit`/`reports`：关键变更审计、日结、渠道对账和异常看板。

`frontend_1` 只保留首页、门票、私汤、订单、会员和储值；移除园内点餐及具体房号选择。`frontend_2` 从房间码进入，展示房号、菜单、购物车、订单和支付方式；最新要求允许在页面顶部手动选择房间号，服务端仍只接受有有效使用记录的房间。点餐页左侧列出营业商家、右侧展示该商家商品，管理员可在 Web 维护商家及商品。访客可微信支付，余额支付必须先登录并验证会员归属。`frontend_web` 按前台、商家、财务、管理员展示独立工作台。`device_service` 仅出站访问后端，不暴露云端需要访问的私有端口。

## 4. 核心数据与状态

权威表包括 Member/Identity、TicketOrder/Ticket/Admission、Room/RoomBlock/PrivateBooking/RoomUse/CleaningRecord、MemberAccount/LedgerEntry、FoodOrder/FoodOrderItem、Payment/Refund、Deposit/Card/Locker/LockerReservation、DeviceTask 和 AuditEvent。订单保存票、房、菜、活动和押金金额快照；OpenID 不跨小程序复用。

私汤可售通过逐房完整区间重叠检查计算：连续场只计算最终一次清洁；同事务锁定候选房并排除有效预占、已确认预约、实际使用、清洁、维护和人工占用。支付确认不得复活过期预占。分房重新以实际开始时间检查完整使用与清洁区间，无房可分时返回冲突，不覆盖已售预约。

账本只在事务内追加流水，并锁定账户；消费先本金后赠送，退款引用原流水分别冲回。支付回调以商户单号幂等，只有渠道验证成功才推进业务。点餐支付再次检查原 `room_use_id`，不可送达则进入人工异常队列而不出餐、不自动退款。每张票只能核验一次；每枚押金只关联一个有效退款号。设备超时与结果未知分离。

## 5. API 与界面契约

公开接口覆盖开发/微信登录、配置与库存查询、订单创建、支付单、订单/票券/余额查询、房间码上下文和点餐。运营接口覆盖人工验票、到店分房、清洁/维护、柜位与发卡、押金归还退款、菜单、出餐状态、异常处理、活动、报表和审计。设备接口仅含主动领取、开始和结果回传。OpenAPI 为接口事实来源；统一错误体包含稳定错误码、说明和请求号。

前端所有操作显示加载、空、失败和结果未知状态；支付后主动查询服务端，不根据客户端回调直接增加余额或显示出餐。Web 对高风险操作要求原因并展示审计结果。界面保留现有温泉纸色/深绿视觉语言，但优先保证表格、状态和操作的清晰度。

## 6. 安全、迁移与运行

提供 `.env.example`、Docker Compose MySQL、Alembic 初始迁移和开发种子数据。鉴权采用签名开发令牌或后续 OIDC/微信适配器，接口同时校验角色和资源归属；支付回调保留验签与金额/商户核对。仓库不复制现有 MCP 配置中的密钥。README 分别说明安装、迁移、种子、运行、测试和真实服务替换点。

## 7. 验证与交付边界

 pytest 覆盖：连续多场仅末次清洁、整段同房库存、15 分钟过期与支付竞争、晚到分房冲突、票券单次入园、本金优先、按来源退款、跨端同账本、重复支付回调、旧 `room_use_id`、逐枚押金退款、重复设备回传及未知结果。MySQL 集成测试验证唯一约束和并发不超卖。前端运行 TypeScript 检查、Vite 构建及可执行的交互测试；小程序执行静态配置/脚本检查并说明微信开发者工具未自动化验证的部分；设备 Mock 跑领取与回传测试。

交付明确区分单元、数据库集成、设备模拟和待真实微信/Windows SDK/NFC/锁样机联调。固定场与晚到满时长政策、取消/部分退款、押金金额、AppID/商户号/UnionID、部署位置及硬件能力保持待确认，不自行补业务政策。
