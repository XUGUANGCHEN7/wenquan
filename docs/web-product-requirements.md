# 蜀南温泉一期运营 Web 产品需求文档（PRD）

> 文档版本：1.0  
> 产品范围：`frontend_web/` 运营工作台  
> 依据：当前 Vue 3 实现、[`backend-system-architecture.md`](./backend-system-architecture.md)、[`backend-api.md`](./backend-api.md)、项目一期规则  
> 发布状态：一期可运行版本；真实微信支付、正式身份服务和 Windows 硬件仍未联调

## 1. 产品概述

### 1.1 产品定位

蜀南温泉运营 Web 是前台、接单商家、财务和管理员共用的浏览器工作台，用同一套服务端事实处理：

- 门票人工核验
- 私汤到店分房、使用、清洁和加钟
- 手牌、柜位和逐枚押金
- 房间点餐接单、制作和送达
- 会员本金/赠送账本、人工退款和日结
- 商家、商品和业务规则配置
- 设备任务、异常和审计

产品不是游客端，不承担购票、预约、点餐和微信支付的主流程；这些动作发生在两个小程序。

### 1.2 核心目标

1. **可核验**：票券、押金、分房、设备操作都能追溯到操作人、时间、原因和请求号。
2. **不重复**：服务端事务与幂等保证不重复出票、不重复扣款、不重复退款、不重复发牌。
3. **不误导**：未知、失败、处理中和成功严格区分，不用 Toast 或前端推断掩盖真实状态。
4. **高效率**：一屏完成高频前台动作，减少在多个系统、表格和聊天记录之间切换。
5. **可控制**：退款、改价、停用商家、修改规则等敏感操作受角色限制并写审计。

### 1.3 核心场景

| 场景 | 触发者 | Web 价值 |
|---|---|---|
| 游客到店验票 | 前台 | 核对每人独立票券，单次入园 |
| 私汤到店分房 | 前台 | 按完整使用+清洁区间重新检查，避免撞场 |
| 结束使用和清洁 | 前台 | 控制房态，未清洁完成不能再次分房 |
| 手牌/柜位发放 | 前台 | 押金、预占、写卡任务一致 |
| 手牌归还与退款 | 前台/财务 | 清卡与逐枚退款解耦，异常可追踪 |
| 房间点餐履约 | 商家 | 只处理支付且可送达订单 |
| 退款和异常处理 | 财务/前台 | 人工决策有事实依据，不自动退款 |
| 商家/商品/规则维护 | 管理员 | 点餐端所见即服务端真实配置 |
| 日结核对 | 财务 | 收入、充值负债、未退押金分开 |

### 1.4 业务痛点

- 票券、私汤、餐饮和储值分散时，难以确认“谁已入园、谁已付费、谁在哪个房间”。
- 单纯按场次显示 17 个名额会超卖；晚到分房会与下一笔预约冲突。
- 多人押金容易混成一笔，退一枚时无法准确对应原微信交易。
- 设备写卡结果未知时盲目重试，可能重复写卡或释放已占用柜位。
- 点餐支付后房间已换客，仍按房号送餐会错送。
- 前台只凭口头或表格记录，无法还原操作责任。
- 运营方看不到本金、赠送、押金和收入的区别，财务口径混乱。

### 1.5 用户群体

| 角色 | 使用设备 | 主要任务 | 权限边界 |
|---|---|---|---|
| 前台核验 | 前台 PC + 读卡器 | 验票、分房、房态、发牌、归还 | 不能改会员余额、不能受理财务退款、不能改系统规则 |
| 接单商家 | 商家 PC/平板 | 查看点餐队列、接单、制作、送达 | 只能处理出餐，不看财务和硬件操作 |
| 财务 | 财务 PC | 账本、人工退款、日结、异常 | 不直接操作实体手牌或柜位 |
| 管理员 | 管理 PC | 全部运营 + 商家商品 + 配置 + 审计 | 高风险动作须留原因；不得绕过审计 |
| 运营负责人 | 任意浏览器 | 查看总览和异常处理进度 | 通过管理员或对应角色执行 |

直接顾客不使用 Web；顾客端是小程序。

### 1.6 成功指标

上线后按日统计，目标值需业务方在试运行后确认：

- 验票人工操作成功率和平均耗时。
- 私汤可售量、实际使用率、因换房/退款造成的损失。
- 点餐支付后到接单、到送达的时长。
- 待处理退款、设备 UNKNOWN、房间冲突、待清洁超时的数量和平均关闭时长。
- 账本冲回错误数、重复支付/退款事件数。
- 设备任务从创建到业务生效的成功率。

## 2. 产品范围与原则

### 2.1 一期范围

包含登录与角色导航、总览、票券核验、私汤房态/分房、商家出餐、手牌柜位、会员账本、异常看板、日结报表、商家商品、规则配置。

### 2.2 明确不做

- 不做闸机自动验票。
- 不做游客端购票、预约、点餐页面。
- 不做自动退款、自动改期、自动补偿。
- 不做会员余额提现。
- 不做真实设备 DLL 操作界面；Web 只创建/展示任务，Windows 本地服务执行。
- 不在浏览器保存微信 AppSecret、支付私钥或设备密钥。

### 2.3 产品原则

1. **服务端是事实**：不信任客户端价格、余额、支付成功、房态和设备结果。
2. **先核对再提交**：高风险操作展示对象、金额、状态和原因。
3. **状态不可混淆**：受理不等于成功，未知不等于失败，写卡不等于开门。
4. **异常可见**：加载失败、无权限、冲突、未知必须留在页面上，不用短 Toast 代替。
5. **最小权限**：角色看不到无关菜单，直接访问受限路由也回退。

## 3. 端到端业务流程

### 3.1 登录到工作台

**入口**：`/login`  
**参与者**：前台、商家、财务、管理员

1. 用户进入登录页，看到四张角色卡及职责说明。
2. 用户选择角色；按钮进入加载态，禁止重复点击。
3. 前端请求 `/auth/dev`（当前开发环境）取得令牌和角色。
4. 令牌与角色保存到浏览器本地存储，跳转到角色默认页：
   - 前台/管理员 → 运营总览
   - 商家 → 商家出餐
   - 财务 → 日结报表
5. 路由守卫校验登录状态与页面角色；无权页面回退总览。
6. 用户从侧边导航进入业务页面，顶栏显示角色和退出。

**失败分支**：接口失败显示 `form-error`，保留登录页；令牌被服务端拒绝后任意请求返回 401，用户应退出重新登录。正式版本不得使用角色卡式开发登录。

**最终目标**：用户进入与其职责匹配的工作台，不看到越权菜单。

### 3.2 门票核验与单次入园

**入口**：`/tickets`  
**前置**：游客持有已支付、未使用票券；前台已人工核对订单与身份。

1. 前台在“票券编号”输入或扫描 `ticket_no`。
2. 填写核验原因；页面自动生成唯一 `request_id`。
3. 提交后按钮禁用，调用 `/operations/tickets/admit`。
4. 成功后清空票号，右侧本次操作记录新增“成功，已记录单次入园”。
5. 后端记录票券为已使用、操作人、时间和原因；同票再次使用新请求号被拒绝。
6. 下一张票重复。

**失败分支**：已使用、已作废、未支付、票号不存在显示后端原因；页面保留输入和错误。网络超时不可自行重试为“已成功”，应先查询/核验。

**最终目标**：每位游客独立完成一次入园，未重复耗票。

### 3.3 私汤到店分房

**入口**：`/rooms`  
**前置**：会员预约已支付确认，游客到店。

1. 前台查看 17 间房实时卡片：房号、房态、结束使用时间、清洁截止时间。
2. 在“到店分房”输入预约 ID，选择实际开始时间，填写处理原因。
3. 提交前端调用分房 API，服务端重新检查：
   - 预约已支付且未过期
   - 实际使用总时长 + 最后清洁区间
   - 候选房后续预约、维修、占用和加钟
4. 成功返回实际房号/使用记录 ID，页面刷新房态。
5. 若返回 `ASSIGNMENT_CONFLICT`，显示冲突原因，不自动覆盖或静默顺延；按业务方改期/退款流程处理。
6. 游客结束使用后，前台点“结束使用”。
7. 房态变“待清洁”；保洁开始后点“开始清洁”，完成后点“清洁完成”。
8. 清洁完成后房间才回到可分配状态。

**最终目标**：实际分房与后续预约、清洁不冲突，房态准确。

### 3.4 手牌、柜位与逐枚押金

**入口**：`/access`  
**前置**：每枚手牌对应独立已付微信押金。

1. 前台查看可用手牌、空闲柜位、已付押金、未知设备任务数量。
2. 选择一枚已付押金和一枚可用实体手牌。
3. 点击“预占柜位并创建写卡任务”。
4. 后端先锁定空柜，再创建 `ISSUE_CARD` 任务；页面显示任务号，提示设备成功前不是正式绑定。
5. Windows 设备服务领取、执行、回读并回传结果。
6. 成功：绑定变 `BOUND`、手牌/柜位占用；页面可刷新看到。
7. 失败：保留可处理状态；未知：现场核实实体卡权限，禁止在 Web 直接重试写卡。
8. 归还时选择已绑定手牌，填写实物核对原因，点“登记实物归还”。
9. 后端立即创建逐枚退款单，同时创建清卡任务；清卡与退款互不阻塞。
10. 清卡成功/失败后，柜位进入待释放；前台确认柜内已清洁，点击“清洁完成并释放”。

**最终目标**：一枚手牌、一枚押金、一次退款、一个柜位责任清晰可追踪。

### 3.5 房间点餐履约

**入口**：`/dining`  
**参与者**：接单商家、前台、管理员

1. 顾客在小程序完成支付且原房间使用记录仍可送达，订单才进入 `QUEUED`。
2. 商家进入出餐页，只能看到已付款、可送达和后续履约订单。
3. 商家点击“接单”；状态 `QUEUED → ACCEPTED`。
4. 点击“开始制作”；状态 `ACCEPTED → PREPARING`。
5. 送达后点击“确认送达”；状态 `PREPARING → DELIVERED`，记录送达时间。
6. 卡片展示房号、订单号、商品明细、金额、下单和送达时间。
7. 不可送达订单不进入队列，在前台/财务异常看板处理。

**失败分支**：非法状态跳转被拒；接口重复点击不重复推进业务；页面需刷新真实状态。

### 3.6 财务退款、账本与日结

**入口**：`/wallet`、`/exceptions`、`/reports`  
**前置**：订单已支付；退款原因经过业务确认。

1. 财务按会员 ID 查询本金、赠送和合计余额。
2. 查看追加式流水，核对原订单引用、本金/赠送扣减和来源。
3. 在人工退款表单输入订单号和原因。
4. 余额支付：后端按原本金/赠送实际扣减冲回，退款成功；微信支付：先受理，等待渠道确认。
5. 财务在异常看板跟踪退款 `ACCEPTED/PROCESSING/UNKNOWN/FAILED`；只有 `SUCCESS` 可显示退款成功。
6. 选择日期查询日结：票券、私汤、点餐、加钟收入分别展示；充值本金/赠送和未退押金作为非收入项展示。
7. 渠道对账差异当前待实现，不在页面自行平账。

**最终目标**：财务数据可解释、可按原来源退款、不把押金或充值算成当日收入。

### 3.7 管理员维护商家与商品

**入口**：`/merchants`  
**前置**：管理员已登录。

1. 左侧商家档案显示商家名称、商品数量、营业状态。
2. 点击“新增商家”，输入名称和营业状态，保存后自动选中新商家。
3. 选中商家后，右侧显示其全部商品；可新增商品。
4. 商品表单填写名称、分类、价格（元）、库存/不限库存、图片地址、描述、可售状态。
5. 价格前端以元输入两位小数，提交前精确转为整数分。
6. 保存后刷新列表；点餐端只展示营业商家的商品。
7. 删除商品前确认；已有历史订单时拒绝，引导改为下架。
8. 删除商家前确认；仍有商品或历史订单时拒绝。
9. 停用商家后不再能接收新订单，但历史订单保留。

**最终目标**：运营人员无需直接操作数据库即可维护点餐端商家和菜单。

### 3.8 异常统一处理

**入口**：`/exceptions`  
**参与角色**：前台、财务、管理员

1. 页面并行加载待处理退款、已付款未交付、设备未知、房间冲突、点餐无法送达。
2. 用户按分类查看对象、状态、金额、原始错误。
3. 退款进入账本人工退款；设备未知转现场核实；房间冲突按改期/退款流程；点餐不可送达由前台决定处理。
4. 所有人工动作写原因和审计；页面不自动退款、不自动改房态、不自动重试设备。
5. 处理后刷新，确认异常从列表消失。

**最终目标**：每个异常有明确负责人、人工依据和闭环记录。

## 5. 关键页面与模块需求

### 5.1 登录页 `/login`

**目标**：用最少步骤进入正确工作台。  
**页面元素**：温泉品牌故事区、四张角色卡（前台、商家、财务、管理员）、当前角色加载态、错误提示、开发 Mock 声明。  
**交互**：

- 点击角色后其他卡禁用，显示“正在进入…”。
- 登录成功跳角色默认页；失败保持页面并显示原因。
- 已登录访问 `/login` 自动回总览。
- 退出清除令牌和角色，回登录页。

**状态**：默认、加载、失败、已登录重定向。  
**验收**：`AC-4.1` 无令牌访问受保护页必须回登录；`AC-4.2` 商家无法看到财务/规则菜单。

### 5.2 运营总览 `/`

**目标**：用一屏回答“今天哪里需要处理”。  
**元素**：

- 指标卡：待处理异常总数、占用中私汤房、支付模式、设备模式。
- 今日工作提示：人工验票、分房冲突、设备未知三条操作原则。
- 异常分类：待处理退款、发卡结果未知、房间冲突、点餐无法送达，可点击进入看板。
- 私汤房即时状态条：17 间房的房号、状态色。
- 角色差异：商家不显示异常汇总与房态，仅提示从商家出餐进入；前台/管理员显示房态。

**交互**：加载失败保留重试；卡片跳转必须带对应角色权限。  
**验收**：`AC-4.3` 不将 Mock 模式显示成真实支付/设备已联调。

### 5.3 票券核验 `/tickets`

**目标**：逐票人工入园。  
**字段**：票券编号（必填）、核验原因/记录（最多 500 字）、自动生成请求号。  
**动作**：确认人工入园。成功后清空输入并在右侧新增本次操作记录；不展示全量历史。  
**状态**：待输入、提交中、成功、失败；失败显示已使用/未支付/不存在等原因。  
**交互规则**：

- 同一次提交必须复用请求号；新请求号再次核验同一票由服务端拒绝。
- 不使用整单核销；多人票逐人操作。
- 成功后不自动把下一张票带入。

**API**：`POST /operations/tickets/admit`。  
**验收**：`AC-4.4` 一票一入园；`AC-4.5` 失败不清空输入，避免前台误操作。

### 5.4 私汤房态与分房 `/rooms`

**目标**：到店分房、结束使用、清洁和维护占用。  
**元素**：

- 17 个房态卡片：房号、状态、结束使用、清洁截止。
- 到店分房表单：预约 ID、实际开始时间、处理原因、提交按钮。
- 维护/人工占用表单：房间、开始/结束、原因。
- 房卡上的操作随状态变化：
  - 使用中 → 结束使用
  - 待清洁 → 开始清洁
  - 清洁中 → 清洁完成

**关键交互**：

- 分房前必须展示“重新检查完整使用与清洁区间”，不能按场次剩余名额直接分配。
- 分房失败必须保留预约 ID 与原因；`ASSIGNMENT_CONFLICT` 不自动改房。
- 分房成功后刷新全房态，显示实际房号和使用记录。
- 清洁完成前房间不可再次分房。
- 结束使用后房态进入待清洁，不直接空闲。

**默认值**：实际开始默认为当前时间；原因为“游客到店，前台重新检查完整使用与清洁区间”。  
**验收**：`AC-4.6` 未清洁房间不能被再分配；`AC-4.7` 冲突时不得显示成功。

### 5.5 商家出餐 `/dining`

**目标**：只处理已支付且可送达订单，并按固定状态推进。  
**元素**：操作原因输入、刷新按钮、订单卡片。每卡包含房号、订单号、状态徽章、商品与单价、合计、下单时间、送达时间、下一动作按钮。  
**动作文案**：`QUEUED` 接单；`ACCEPTED` 开始制作；`PREPARING` 确认送达；`DELIVERED` 无下一步。

**规则**：

- 不显示 `NOT_READY` 和 `EXCEPTION` 到正常出餐队列。
- 每次状态推进填写原因，写审计。
- 按钮点击后禁用直至完成；失败保留真实状态，不乐观跳步。
- 刷新可能改变队列；页面不缓存旧状态当事实。

**API**：`GET /operations/dining/orders`、`POST /operations/dining/orders/{id}/transition`。  
**验收**：`AC-4.8` 商家只看得到其权限范围队列；`AC-4.9` 非法跳转必须失败。

### 5.6 手牌柜位 `/access`

**目标**：完成“押金 → 预占柜位 → 写卡 → 绑定 → 归还 → 退款/清卡 → 释放柜位”闭环。  
**指标卡**：可用手牌、空闲柜位、已付押金、设备 UNKNOWN。  
**区域**：

- 发牌并写卡：已付押金、可用实体手牌。
- 归还与独立退款：已绑定手牌、归还核对原因。
- 柜位列表：编号、状态、清洁完成释放。
- 设备任务：最近 15 条任务类型、状态、原始错误/任务号。

**关键交互**：

- 未选押金/手牌不能提交；提交后提示“创建设备任务，设备成功前不是正式绑定”。
- 归还成功提示独立退款单和清卡任务号；退款与清卡不互相阻塞。
- 清卡失败不剥夺退款；卡片进入隔离，不能再次选择。
- UNKNOWN 任务不出现“重试写卡”按钮，只提示现场核实。
- Web 不模拟开门成功，不展示“门已打开”。

**验收**：`AC-4.10` 未知结果不自动释放柜位；`AC-4.11` 归还生成独立退款单。

### 5.7 会员账本 `/wallet`

**目标**：财务查询统一储值账本并受理人工退款。  
**元素**：

- 会员 ID 查询框。
- 三张指标：本金余额、赠送余额、合计可用。
- 流水表：类型、业务引用、本金变动、赠送变动、双方余额、时间。
- 人工退款表单：订单号、原因、提交。

**交互规则**：

- 余额显示为元、两位小数，后端仍分。
- 消费扣减来源必须本金优先；退款按原扣款来源冲回。
- 微信退款只显示受理，渠道未确认前不能显示“退款成功”。
- 押金不能走通用订单退款；提示走逐枚归还流程。
- 查询失败不得保留上一会员账本冒充当前结果。

**API**：`GET /operations/wallet/{member_id}`、`POST /operations/orders/{order_no}/refunds`。  
**验收**：`AC-4.12` 本金/赠送分列且合计正确；`AC-4.13` 退款状态不提前成功。

### 5.8 异常看板 `/exceptions`

**目标**：集中展示人工必须介入的五类异常。  
**模块**：

1. 待处理退款：退款号、状态、金额。
2. 已付款未交付：订单号、类型、金额、状态。
3. 发卡结果未知：任务号、原始错误。
4. 房间占用冲突：预约 ID、冲突状态。
5. 点餐无法送达：原因。

**交互**：刷新；按类别展示计数；空列表显示 0；不得提供“一键退款/重试写卡/自动改房”等未经确认动作。  
**验收**：`AC-4.14` 五类异常均可见；`AC-4.15` 页面不自动修改资金或设备状态。

### 5.9 日结报表 `/reports`

**目标**：查看经营收入与负债边界。  
**元素**：日期选择、七张指标卡：票券收入、私汤收入、点餐收入、加钟收入、充值本金、充值赠送、未退押金。  
**交互**：选择日期后查询；无数据时显示空状态，不将无数据视为 0 收入。  
**文案要求**：充值本金/赠送、未退押金必须标为“非收入/负债”。  
**已知缺口**：微信渠道账单导入和差异记录未实现，页面只展示业务事实。  
**验收**：`AC-4.16` 押金不计入收入；`AC-4.17` 四项收入与三项非收入分开展示。

### 5.10 商家商品 `/merchants`

**目标**：管理员通过页面维护点餐端商家与商品。  
**布局**：两栏。左栏商家档案与新增/编辑；右栏当前商家商品与商品表单。  
**商家字段**：名称、营业中。  
**商品字段**：名称、分类、价格（元，两位小数）、库存/不限库存、图片 URL、描述、可售。  
**操作**：

- 新增/保存商家；删除需二次确认。
- 新增/保存商品；删除需二次确认。
- 商家仍有商品/历史订单时删除失败，显示后端原因。
- 商品有历史订单时删除失败，引导下架。
- 停用商家在点餐端不可见且不能接新单。
- 价格输入失焦格式化为两位小数，提交精确转换为整数分。
- 所有动作成功后刷新并保留当前商家上下文。

**验收**：`AC-4.18` 商家/商品 CRUD 可用；`AC-4.19` 删除受限时不产生孤儿数据。

### 5.11 规则配置 `/settings`

**目标**：维护已确认的基础价格、时长、票种价格、充值活动、房间码。  
**模块**：

- 基础价格与时长：私汤基础价（元）、手牌押金（元，待确认）、加钟价格（元）、加钟时长（分钟）。
- 节假日票种价格：日期、成人价（元）、儿童价（元）。
- 充值活动：活动名、本金、赠送余额、启用。
- 房间码：记录编号、启用、保存并重印（版本 +1）。
- 辅助菜单价格/库存：作为兼容维护入口，完整商品管理以“商家商品”页为准。

**规则**：金额输入为元并保留两位；保存后回填规范化；未确认政策不在页面自动生成默认公式。  
**验收**：`AC-4.20` 金额不出现浮点误差；`AC-4.21` 不暴露未支持配置键。

## 6. 关键交互与状态规则

### 6.1 通用交互

| 场景 | 规则 |
|---|---|
| 页面加载 | 优先展示 `DataState` 加载态；禁止先显示假数据 |
| 请求失败 | 保留错误和重试；表单错误留在表单附近 |
| 提交按钮 | 提交中禁用，防重复点击；失败恢复可用 |
| 列表刷新 | 操作后主动刷新服务端状态，不本地猜测 |
| 金额 | 输入/显示元且两位小数，提交转整数分 |
| 空状态 | 说明“为什么为空”和下一步，不显示 0 冒充数据 |
| 破坏性操作 | 删除/停用/退款二次确认，说明影响 |
| 角色 | 菜单隐藏 + 路由守卫 + 服务端鉴权三层一致 |
| 长文本 | 订单号/任务号用等宽字体，允许换行 |
| 日期时间 | 本地化中文显示；提交统一 ISO 8601 |

### 6.2 状态语义

**房态**：`FREE` 空闲、`ACTIVE/IN_USE` 使用中、`PENDING_CLEANING` 待清洁、`CLEANING` 清洁中、`MAINTENANCE` 维护。  
**订单**：`PENDING` 待支付、`PAID` 已支付、`EXCEPTION` 需人工处理、`REFUNDED` 已退款。  
**点餐履约**：`NOT_READY` 待支付、`QUEUED` 待接单、`ACCEPTED` 已接单、`PREPARING` 制作中、`DELIVERED` 已送达、`EXCEPTION` 人工异常。  
**退款**：`ACCEPTED` 已受理、`PROCESSING` 处理中、`SUCCESS` 渠道成功、`FAILED` 失败、`UNKNOWN` 结果未知、`CLOSED` 关闭。  
**设备**：`PENDING` 待领取、`CLAIMED` 已领取、`RUNNING` 执行中、`SUCCEEDED` 成功、`FAILED` 失败、`UNKNOWN` 待核实。  
**押金/手牌**：`PAID` 已付、`REFUND_PENDING` 退款中、`REFUNDED` 已退、`ISSUING` 发卡中、`BOUND` 已绑定、`CLEARED` 已清卡、`CLEAR_FAILED` 清卡失败、`QUARANTINED` 隔离。

颜色语义：

- 绿：正常、成功、进行中。
- 米金/琥珀：待清洁、待处理、待领取。
- 红：失败、冲突、未知、人工异常。
- 灰：已结束、无数据或历史。

不得只用文字改变含义；状态必须同时有文本标签。

### 6.3 高风险动作确认

- 退款：确认订单号、金额、支付方式、原因；明确微信退款受理不等于成功。
- 删除商家/商品：确认对象和影响；有引用时展示服务端拒绝原因。
- 停用商家：提示点餐端立即可见性变化。
- 分房冲突：不提供“强制覆盖”按钮；通过业务签认的改期/退款流程。
- 设备 UNKNOWN：不提供 Web 端“重试写卡”；展示核实实体卡的提示。
- 修改加钟/押金金额：提示开发种子不等于正式政策。

## 7. UI 设计规范

### 7.1 整体布局

```text
┌──────────────┬──────────────────────────────────────────┐
```

### 7.4 间距、圆角与层级

- 基础间距 4px；常用 8/12/14/18/22/24/34px。

- 阴影：`0 5px 20px rgba(53,56,44,.035)`，仅面板轻微阴影。
- 页面背景与卡片表面形成轻微层次；不使用大面积强渐变、玻璃拟态或发光。

### 7.6 响应式

| 宽度 | 行为 |
|---|---|
| >1050px | 238px 全文字侧栏；指标 4 列；双栏面板 |
| 721–1050px | 76px 图标侧栏，隐藏品牌文字；指标 2 列；双栏变单栏 |
| ≤720px | 侧栏变顶部横向导航；页面头纵排；表单两列变单列；房间/订单单列或自动换行 |

- 触控目标至少 40×40px（移动）。
- 表格不压缩字到不可读；使用横向滚动。
- 长订单号、设备错误用 `word-break`，不撑破卡片。
- 不依赖 hover 完成关键业务；所有操作可点击/聚焦完成。

### 7.7 反馈与可访问性

- 加载显示 spinner 与文案，不用空白页。
- 成功使用绿色提示条；错误使用红色且保留。
- 错误信息必须包含可执行下一步（重试、修改输入或联系角色）。
- 键盘 focus 可见；按钮/输入有可读 label；颜色不是唯一信息。
- 尊重 `prefers-reduced-motion`（正式版补充）。
- 不使用小字号作为业务关键信息的唯一载体。

## 8. 非功能需求

### 8.1 性能与稳定性

- 首屏目标：常用页面在正常办公网络下 2 秒内出现加载态，5 秒内完成首屏数据请求；目标值需现场验收。
- 所有请求设置超时和失败提示；禁止无限等待。
- 页面刷新和操作后从服务端重新拉取关键状态。
- 一期不做自动轮询的硬性要求；出餐、房态需要操作后刷新或定时刷新，正式频率待运营确认。
- 单个页面请求失败不得阻塞其他页面；总览中商家无权模块可以不请求。

### 8.2 安全与隐私

- 不在 Web 保存 AppSecret、微信支付私钥、设备卡密钥。
- 令牌只存浏览器本地存储，正式版必须重新评估 XSS 防护、短期会话和刷新机制。
- 后端角色校验是最终权限，前端隐藏菜单只改善体验。
- 不展示完整游客敏感信息；只显示业务需要的会员 ID、订单号、房号。
- 所有人工敏感操作填写原因并进入审计。
- 生产必须 HTTPS；CORS 限制到运营 Web 域名。

### 8.3 数据一致性与错误处理

- 不把“请求已发出”显示为“业务成功”。
- 支付、退款、设备、房间状态以服务端返回为准。
- 使用 `request_id` 关联错误；冲突时保留原订单/票号，不创建第二笔。
- 列表无分页接口，当前是固定上限；超过上限的运营查询应明确提示，不作为完整历史导出。

- 目标浏览器：最新版 Chrome/Edge；前台 Windows PC 优先。
- 最小宽度 320px；平板和手机可读但核心前台操作仍建议桌面。
- 不依赖浏览器扩展或本地 DLL；设备操作全部经后端任务。

## 9. 验收标准与测试

### 9.1 关键验收清单

1. 角色登录、越权路由和退出。
2. 同一票两次入园被拒绝，重复请求号幂等。
3. 私汤分房冲突不覆盖后续预约，未清洁不能分房。
4. 出餐状态只能按固定顺序推进，重复点击不重复推进。
5. 发卡/归还/清卡失败与退款状态互不混淆。
6. 本金优先、赠送后扣，退款按原来源冲回。
7. 商家/商品 CRUD，及有历史订单时禁止删除。
8. 金额输入元两位小数与后端整数分转换。
9. 五个异常类别的列表、空状态和错误状态。
10. 日结四项收入、三项非收入边界。
11. 1050/720 宽度下导航、表单、表格和卡片布局。
12. 所有失败操作保留可执行错误，不显示假的成功状态。

### 9.2 自动化与人工验收

- 已进行：Web Vitest 8 项、TypeScript 类型检查、Vite 生产构建。
- 需补：页面组件测试、端到端浏览器测试、真实 API 联调回归、屏幕阅读器/键盘验收。
- 支付、退款、设备真实结果必须由渠道/设备联调报告确认，不能用 Mock 单测替代。

## 10. 当前实现差距与迭代建议

| 优先级 | 差距 | 影响 | 建议 |
|---|---|---|---|
| P0 | 手牌页没有“创建押金订单”和“未发牌押金退款”入口 | 前台无法完整从前端发起押金流程 | 使用后端已有 `/operations/deposits/orders`、`/deposits/{id}/refund` 补 UI |
| P0 | 登录仍是开发角色卡，无正式身份/会话 | 不能投入生产 | 接入受控身份服务、Web 登录与令牌刷新 |
| P0 | 退款正式渠道确认未接入 | 微信退款无法真实闭环 | 接入退款通知/查询、对账和人工异常流程 |
| P1 | 房态页未提供加钟操作入口 | 前台需通过 API 才能加钟 | 增加绑定手牌选择、价格确认、设备任务状态 |
| P1 | 商家角色没有真实商家数据隔离 | 多商家时可能看到全队列 | 增加 merchant_id 范围绑定和测试 |
| P1 | 异常看板只读 | 处理需要切换页面/外部流程 | 增加受控跳转、处理记录、负责人字段（需业务确认） |
| P2 | 规则页仍保留辅助菜品修改 | 与“商家商品”重复 | 统一到商家商品页，规则页只保留规则 |
| P2 | 无正式浏览器 E2E 和自动刷新 | 高频前台效率有限 | 增加 Playwright、轮询/刷新策略 |
| P2 | 渠道账单未导入 | 日结缺对账依据 | 增加对账模块和差异处理 |

## 12. 发布判定

满足以下条件才可标记“生产可发布”：

- P0 差距全部关闭。
- 后端迁移、MySQL 并发、支付/退款、设备联调报告齐全。
- Web 与 API 角色矩阵通过端到端验收。
- 业务方对流程、政策、异常处理书面签认。
- 本 PRD 中的 Mock/待确认项不再出现在生产默认路径。

在此之前，本产品应标注为**一期可运行/联调版本**，不得对外宣称真实支付、真实硬件或生产安全已经完成。
