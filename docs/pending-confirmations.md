# 一期待确认与未联调事项

本文件区分“代码已实现的可运行骨架”和“必须由业务方、微信平台、设备商或现场确认后才能生产使用”的内容。任何 Mock 成功都不代表真实资金或硬件成功。

## 业务政策

1. 固定预约场次与实际分房后满 120 分钟的冲突处理、告知、改期、补偿和退款权限。
2. 每枚手牌的押金金额、损坏/遗失责任、真实微信支付部分退款次数/商户能力、异常退款人工处理权限。
3. 门票与私汤取消规则；点餐顾客主动取消、部分退款、缺货退款规则。
4. 储值余额退还/提现规则（一期明确不实现自动退余额）。
5. 儿童票适用规则与价格、节假日日期表及调价审批流程。
6. 点餐端已按要求允许手动选择房间号；服务端仍校验房间处于有效使用中，但无法证明点餐人实际在该房间。是否需要额外在场核验、防误送确认或异常撤单流程待业务方确认。

代码只维护配置字段和人工异常事实，不自行生成上述默认公式。当前 `deposit_amount_cents=10000`、`extension_price_cents=12000`、`extension_minutes=120` 等是开发种子，不是经业务确认的正式政策。

## 微信身份与支付

1. 两个小程序正式 AppID、AppSecret 受控保存方式。
2. 两个 AppID 对应的商户号关系、支付权限、退款权限和单笔部分退款能力。
3. 是否可取得 UnionID；不可取得时，点餐端绑定已有 `member_id` 的安全一次性授权与身份校验流程。
4. 正式微信登录代码、OpenID 映射、支付预下单、`wx.requestPayment`、回调验签、商户/金额核对、主动查询和退款通知。
5. 当前 `POST /payments/{payment_no}/mock-confirm` 只允许开发环境且不调用微信，生产配置会关闭，不能作为支付证据。

## Windows 与锁具硬件

1. 正式 Windows DLL/SDK、USB NFC 读写器型号、32/64 位、ABI、依赖、许可证和安装方式。
2. 柜锁、私汤定时锁的卡片权限结构、扇区/密钥管理、授权有效期、加钟是否重写、挂失撤销和清卡结果。
3. 同一实体手牌能否同时持有柜锁与私汤锁权限。
4. 断外网后已发手牌能否独立开锁，以及恢复网络后的结果补传。
5. 门磁或可信开门事件是否存在；写卡/读回成功不能证明门实际打开。
6. 当前 `device_service` 只有 `MockAdapter`；不得把模拟成功写成硬件联调完成。

## 部署与运营

1. 云端或园区本地部署位置、服务器规格、MySQL 版本/备份方案、现场网络拓扑和证书管理。
2. 外网中断时的前台应急流程、离线支付/核验的明确禁止项和恢复对账步骤。
3. 日结关账时间、微信渠道账单下载方式、对账差异责任人及处理时限。
4. 异常看板中退款、设备未知、房间冲突、点餐无法送达的人工处理 SLA。
5. 商家账号范围：演示数据只有一个商家，管理员现可维护多个商家及商品；是否一商家一账号、商家只能看自己订单及菜单审核流程仍待确认。

## 已完成但需其他环境验收

- WXML 渲染和交互：需要微信开发者工具/真机。
- 真实微信支付与退款：需要正式 AppID、商户号和密钥。
- MySQL 并发测试：代码已存在；本次环境没有可用 Docker 引擎或 MySQL 测试凭据，未执行。私汤库存和加钟锁的并发保证因此只能视为“领域逻辑已验证、MySQL 并发待验证”。
- Web 浏览器视觉/交互冒烟：类型检查和生产构建通过，未做浏览器自动化或用户验收。
- Windows 设备实机：Mock 单元测试通过，未连接任何真实读写器或锁具。
